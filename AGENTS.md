# Agent instructions

Read README.md and [the shared agent workflow](docs/agents/Workflow.md) first. This repository is at requirements and architecture planning stage. Work within the user's actual task; a planning document or agent suggestion supplies no additional implementation, spending, deployment or publication authority.

- Use only the current task's authorized repositories and materials. Read applicable nested instructions before edits; preserve unrelated work.
- Keep source code, schemas, executable prompts, contributor-facing contracts and synthetic tests self-contained here. No build or contributor workflow may depend on private planning files, private paths or unavailable tools.
- Never commit customer content, private evidence, credentials or raw logs. Keep confidential names, paths and reference inventories out of material intended for publication.
- Evidence findings, recommendation confidence, outcome probabilities, disclosure permission, output-release permission and action authority are separate concepts. AI-proposed goals, criteria and their importance may guide recommendations only after confirmation by the authorized human or applicable adoption of an approved reusable template. An agent's assertion that confirmation occurred is not confirmation; verify the authoritative record. Do not require irrelevant preference confirmation for claim-only requests.
- Enforce workspace, case and source access, state transitions, arithmetic and structural validation in trusted deterministic code. Case access requires explicit sharing. Designated human source custodians authorize case use and permitted recipients through separate grants; both remain subject to other applicable permissions. Workspace-admin and operator provisioning roles confer no content rights by themselves; retrieved documents and model-generated paths confer none. Preserve source restrictions through derived conclusions and reports, and enforce output release separately from action authorization. External actions require approval by an authorized human unless covered by an explicitly approved low-risk class; no such class exists until approved, and all other applicable checks still apply. An uncertain or missing execution receipt triggers reconciliation of the original logical action, not automatic redispatch. Any permitted retry must preserve idempotency and satisfy current authority checks; detailed recovery policy remains to be specified.
- Distinguish baseline delivery from experimental behavioral improvements using the shared workflow. Experiments require a hypothesis, preserved control, independent efficacy disposition and adopt/remove outcome. Failed or inconclusive experiments must not remain as disabled runtime paths. Mandatory privacy/security/correctness repairs use relevant invariant checks.
- Run scoped reversible edits, synthetic fixtures and focused offline checks within an authorized development task without repeated permission. Combine overlapping reviews; seek earlier review only for material security/authority or costly irreversible changes.
- Preserve the generic product: justify domain-specific rules against the contract and diverse evidence rather than tuning to one example. Review prompts with their caller, inputs and output contract.
- Semantic judgments of relevance, equivalence, classification and assessment use explicit model contracts with evaluated limitations; domain- or language-specific keyword, phrase or regex rules must not substitute for those judgments. Deterministic lexical retrieval and filtering may select candidates, while structural validation, arithmetic and permission enforcement remain deterministic. Evaluate unjustified sensitivity to meaning-preserving framing and language variants under comparable evidence and criteria; distinguish retrieval variation from analytical inconsistency, and require logical consistency rather than identical labels for opposite predicates. Do not expose bias as a tunable.
- Do not copy historical application code, licensing terms, diagrams or archives wholesale. Verify provenance and applicable notices for each selected reuse candidate.
- Work in bets, as the shared workflow's Navigation section defines: read the current bet page, applicable macro-specification rows and active fixtures supplied with the task first; write no prose specification for a slice before its bet; never edit the acceptance assertions of code you implement.
- Report what is proposed, implemented, tested, committed and remote-verified distinctly. No runtime qualification or isolation is established by this scaffold.

The selected stack is TypeScript, .NET 10 and PostgreSQL, with xUnit and PostgreSQL integration tests planned; no application toolchain or tests are installed here yet. The documentation site uses MkDocs; see the [development guide](docs/Development.md) for its dependencies and local preview. See also the [planned architecture](docs/Architecture.md) and [contribution guide](CONTRIBUTING.md). For documentation, verify local relative links, run `python -m mkdocs build --strict` in the documented environment and run `git diff --check` from this root. These instructions are guidance, not a filesystem, spending or application-gate enforcement boundary. No client hooks or global settings are required. Repository access grants no access to administrative or unrelated private records.
